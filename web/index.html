An agent can say it finished. That is not the same as it finishing.

Tool calls return success codes. A success code is not proof the customer message actually posted, or that the ticket actually updated. Verity treats those as two separate facts, and checks both.

Step 01 — Flag

Verity reads every account against its own normal rhythm, not a number that applies to everyone. A customer quiet for thirty days is not stalled if thirty days is normal for them.

Step 02 — Draft

A short, specific reason and a draft outreach message go to Slack. Nothing reaches a real customer without a human approving it first.

Step 03 — Verify

After the run, Verity reopens Slack and Linear on its own and checks what is actually there. The agent's claim and the real state have to agree by evidence, not assumption.

The agent's own word is never the last word. A separate piece of code, with its own read access, checks reality after every run.

What actually broke, and what that proved

54.3%
Most agent failures are invisible
Published research on multi app agents found over half of failed runs looked complete right up until the final, human facing step.
So Verity checks the final step independently, every run, not just the steps before it.
1
A real bug, not a staged one
The agent reported a Slack message had posted. It had not. A missing permission scope was the actual reason.
So the scope was fixed, then re-verified with the same independent check, not a new claim.
0
Duplicate writes across reruns
Running the same account twice never creates a second message or a second ticket.
So a local ledger remembers exactly what already happened, before anything is sent again.
12
Hard limit on every run
An agent loop with no ceiling can, in principle, run forever on a bad day.
So every run stops and reports at step twelve, no exceptions, no override.

Asked plainly, answered honestly

Does Verity verify Airtable too?+

No, not yet. The agent only reads from Airtable in this build, it never writes back, so there is nothing on that side to independently confirm. That would be the next system to add.

What happens if Slack and Linear disagree with each other?+

Right now they are checked independently. A ticket referencing a message that was later deleted would still pass both checks separately. Cross checking the two against each other is the next reliability layer, not this one.

Can a customer message actually go out without a human?+

No. Every outreach is a draft posted to Slack for approval. Nothing reaches a real customer automatically.

What happens if Slack or Linear is down?+

Verity retries rate limits and server errors with backoff, gives up cleanly if a service stays down, and reports exactly what got written and what did not, rather than pretending everything worked.

Can someone break it by writing something strange into a customer notes field?+

It has been tested against exactly that. Instructions hidden inside account data are treated as data, never as commands, because the list of things the agent is allowed to do is enforced in code, not just requested in a prompt.

Why Groq instead of a larger frontier model?+

Speed matters for a step by step agent loop a human is meant to watch and approve close to real time. This tool calling does not need the largest model available, it needs a fast, reliable one.
